# Инструкции для AI-агентов и разработчиков

## Назначение проекта

Это платный адаптивный веб-сервис изучения английского языка для русскоязычных взрослых уровней A1-B2 с моделью знаний ученика, детерминированным планировщиком, проверенным каталогом упражнений, ИИ-тьютором и коучингом.

Единственный источник требований продукта: [`Техническое задание.md`](./Техническое%20задание.md). Перед реализацией функции найди соответствующие требования `FR-*`, этап и критерии приёмки. Не расширяй объём проекта без явного запроса.

## Рабочий режим

1. Сначала изучи ТЗ, существующий код, миграции, OpenSpec-артефакты и локальные соглашения. Не предполагай наличие ещё не созданных файлов.
2. Для нетривиальных изменений используй OpenSpec: предложение/спецификация должны фиксировать требования, дизайн и задачи до реализации. Выполняй задачи вертикальными срезами: пользовательский сценарий, серверная логика, БД, интерфейс, тесты.
3. Держи один небольшой законченный срез за раз. После каждого среза запускай релевантные генераторы, тесты и проверки.
4. Не отмечай задачу выполненной без проверки результата. В итоговом сообщении указывай изменённые файлы, тесты и оставшиеся блокеры.
5. Если требование неоднозначно, зафиксируй допущение в `docs/adr/` или задай вопрос. Не угадывай параметры внешних API: проверь официальную документацию и дату проверки.
6. Не перезаписывай пользовательские изменения. Перед редактированием проверь `git status` и работай с текущим состоянием файлов.

## Архитектура и стек

- Модульный монолит: один Go-модуль, исполняемые файлы `web` и `worker`.
- Go актуальной стабильной версии, Gin, Templ, HTMX 2, Pico.css 2 и собственный `app.css`.
- PostgreSQL 16+, pgx v5, sqlc, golang-migrate. ORM запрещён.
- River для фоновых задач поверх PostgreSQL; Redis и отдельный брокер не добавлять.
- Админка: Vue 3, Vite, TypeScript, Pinia, Vue Router, PrimeVue, TanStack Query. Статика собирается и встраивается в Go-бинарник через `go:embed` и доступна с `/admin`.
- SRS: `go-fsrs`. Логи: `slog` в JSON. Метрики: Prometheus. Тесты: `testing`, `testcontainers-go`, Playwright.
- Docker Compose и Caddy для эксплуатации на FirstVDS. PostgreSQL и резервные копии должны находиться в РФ.

Целевая структура:

```text
/cmd/web              /cmd/worker
/internal/platform    /internal/auth       /internal/user
/internal/curriculum  /internal/exercises  /internal/placement
/internal/planner     /internal/srs        /internal/tutor
/internal/voice       /internal/writing    /internal/coach
/internal/billing     /internal/quota     /internal/content
/internal/llm         /internal/speech     /internal/notify
/internal/admin       /internal/jobs
/web/templates        /web/static
/admin                 /migrations          /deploy
/docs
```

Зависимости направлены внутрь домена. Бизнес-модули не импортируют конкретные провайдеры. Пакеты `llm`, `speech` и `billing/provider` не импортируют бизнес-модули.

## Правила реализации

### Данные и SQL

- Каждое изменение схемы выполняй отдельной парой `migrations/NNNN_name.up.sql` и `.down.sql` через golang-migrate.
- SQL храни в `internal/**/queries/*.sql`, генерируй код sqlc и проверяй сгенерированный SQL вручную.
- Не используй ORM, конкатенацию SQL и непараметризованные запросы. Для крупных таблиц проверяй планы через `EXPLAIN`.
- Время храни как `timestamptz` в UTC, деньги как `bigint` в копейках, идентификаторы как `bigint identity`. JSONB применяй только для полиморфных payload/result.
- Используй внешние ключи, ограничения, уникальные индексы и `ON DELETE` по смыслу. Миграции должны быть обратно совместимыми: сначала расширение, затем код, затем очистка.
- Повторная отправка ответа, webhook, River-задачи и платёжные операции должны быть идемпотентными.

### HTTP, Templ и HTMX

- Templ рендерится через `component.Render(ctx, writer)`; `c.HTML` не используется.
- Без `HX-Request` отдавай полноценную страницу, с `HX-Request` -- HTML-фрагмент. После успешного POST применяй `HX-Redirect` или возвращай фрагмент.
- Страницы должны работать при прямом открытии и без обязательного JavaScript. JS допускается только в островах, прежде всего `voice.js` и `timer.js`.
- SSE тьютора передаёт только события `token`, `done`, `error`; данные экранируются на сервере, Markdown-рендеринг ответа модели запрещён.
- HTMX, SSE-расширение и Pico.css храни локально в `web/static` с версией в имени. CDN не используй.
- Пользовательский текст, ответ модели и ошибки выводи с автоэкранированием. `templ.Raw` для таких данных запрещён.
- Для всех ответов добавляй CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy` и `Permissions-Policy`. Inline-скрипты запрещены.

### Внешние сервисы

Все внешние интеграции скрыты за интерфейсами с `context.Context`: `LLM`, `Transcriber`, `Synthesizer`, `PronunciationAssessor`, `PaymentProvider`, `Mailer`, `ObjectStore`.

- Конкретный провайдер выбирается конфигурацией, бизнес-логика не знает его имени.
- Для каждого интерфейса поддерживай mock/fake для тестов и локальной разработки.
- Таймауты, retry, circuit breaker и fallback chain задаются конфигурацией. Повторяй только сетевые ошибки, 5xx и 429; не повторяй неидемпотентные действия без idempotency key.
- Каждый вызов LLM/ASR/TTS записывай с назначением, провайдером, моделью, объёмом, стоимостью, задержкой, статусом и `trace_id`. Содержимое запросов и ответов не логируй.
- В LLM, ASR и TTS передавай только обезличенный учебный контекст: email, имя и другие идентификаторы запрещены.
- Секреты читаются только из env; не добавляй ключи в код, YAML, тестовые fixtures или git.
- Для структурированных ответов LLM используй строгую схему, валидацию и один ремонтный запрос; невалидный результат после повтора обрабатывай как контролируемую ошибку.

### Безопасность и приватность

- Выполняй минимум OWASP ASVS L1. Сервер является источником истины; скрытие кнопки не заменяет авторизацию.
- Пароли: argon2id в PHC-формате, параметры из конфига, ограничение параллельного хэширования. Ошибка входа единая: «неверный email или пароль».
- Сессии: случайный `sid`, в БД только SHA-256, `HttpOnly`, `Secure`, `SameSite=Lax`, ротация при входе и смене пароля. CSRF обязателен для всех не-GET запросов; webhook имеет отдельную проверку.
- Роли `user`, `reviewer`, `admin` проверяй middleware на сервере для каждого маршрута. Все мутации админки пишутся в `audit_log`.
- Не логируй пароли, токены, email, тексты диалогов, голос и другие персональные данные. Пользовательское аудио обрабатывай в памяти и не сохраняй.
- Учитывай 152-ФЗ: хранение и бэкапы в РФ, минимизация данных, удаление аккаунта в течение 30 дней, обезличивание платёжных записей. Юридические требования перед запуском сверяй с юристом.
- Не подключай зарубежную оценку произношения без юридической проверки трансграничной передачи и отдельного согласия.

### Доменная логика

- Проверка закрытых упражнений, нормализация, placement/Rasch, планировщик, FSRS, квоты и конечный автомат заказов -- детерминированный Go-код без LLM.
- Планировщик обязан быть детерминированным при фиксированном времени и seed; учитывай повторы, слабые места, prerequisites, goal weights, пропорции, лимиты новых навыков и content gaps.
- Ученику доступны только упражнения со статусом `published`. Контент, сгенерированный моделью, проходит JSON Schema, автоматические проверки и человеческое ревью до публикации.
- Квоту проверяй до вызова внешнего сервиса и списывай после успешного результата атомарным UPSERT. При fallback-ошибке списание не выполняй.
- Платёжный webhook не доверяет телу: запроси платёж у ЮKassa, сверь статус, сумму и `order_id`, а затем в одной транзакции обнови заказ, платеж и entitlement.
- Формулируй результат `read_aloud` как «разборчивость», а не «правильность произношения».

## Тестирование и проверки

Минимум перед завершением среза:

```bash
go test ./...
go vet ./...
templ generate
sqlc generate
```

По мере появления конфигурации и фронтенда добавляй:

```bash
golangci-lint run
govulncheck ./...
npm ci
npm run build
npm audit
npx playwright test
```

Реальные команды проекта должны быть описаны в `README.md` и CI после появления соответствующих файлов. Не подменяй интеграционные тесты моками там, где нужен настоящий PostgreSQL: используй `testcontainers-go`. Для критичных сценариев обязательны тесты на auth, CSRF, роли, квоты, оплату/webhook, планировщик, прохождение занятия и права доступа. Для адаптеров используй `httptest` и записанные ответы провайдеров. Для пользовательских потоков добавляй Playwright E2E.

Измеряй и проверяй целевые ограничения ТЗ: p95 обычных страниц до 300 мс, проверка упражнения до 150 мс, первый токен тьютора p50 до 2 с, 150 одновременных сессий, отсутствие более 1% ошибок в нагрузочном тесте. Ключевые пакеты `auth`, `billing`, `planner`, `exercises`, `placement` должны иметь покрытие не ниже 70%.

## Работа с OpenSpec и документацией

- Сохраняй продуктовые решения, которые нельзя восстановить из кода, в коротких ADR в `docs/adr/`.
- Храни JSON-схемы упражнений в `docs/schemas`, эталонные наборы промптов в `docs/evals`, OpenAPI 3.1 для админки в `docs` или согласованном каталоге.
- Версии промптов не редактируй на месте: создавай новую версию, проводи eval и активируй только после проверки регрессий.
- Для этапов и изменений явно указывай, какие `FR-*` закрыты, какие тесты подтверждают приёмку и какие внешние предпосылки остаются неподтверждёнными.

## Этапы реализации

Соблюдай порядок из ТЗ:

1. Этап 0: каркас репозитория, CI, Docker Compose, конфигурация, миграции, логи, Templ/Pico, Vue-админка, `/healthz`, деплой, бэкап и восстановление.
2. Этап 1: auth, каталог и ревью, упражнения, FSRS, planner, placement, billing/trial/квоты, текстовый тьютор, дашборд и email-коучинг.
3. Этап 2: голос, AudioWorklet, SpeechKit, `read_aloud`, listening/dictation, TTS и голосовые квоты.
4. Этап 3: проверка письма, недельные отчёты, удержание, B1/B2, TOTP и корректировки по пилоту.
5. Этап 4: внешний `PronunciationAssessor` только после проверки оплаты, права передачи данных и пилота на 50 записях.

Каждая задача должна быть привязана к вертикальному срезу и содержать критерии приёмки. Параллельно с кодом отслеживай внешние блокеры: ЮKassa, уведомление Роскомнадзора, юридические документы, домен и почту, лицензии контента, доступы LLM/SpeechKit и подготовку A1-A2 контента.
