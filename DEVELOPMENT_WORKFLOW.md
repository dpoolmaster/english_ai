# Работа над проектом отдельными сессиями

Каждый законченный срез разработки можно выполнять в отдельной сессии AI-ассистента. Контекст проекта хранится в `AGENTS.md`, техническом задании, OpenSpec-артефактах и самом коде — переносить всю историю переписки не требуется.

## Основные документы

- [AGENTS.md](AGENTS.md) — правила работы над проектом.
- [Техническое задание.md](Техническое%20задание.md) — продуктовые требования и критерии приёмки.
- [proposal.md](openspec/changes/plan-local-first-implementation/proposal.md) — область первого релиза.
- [specs/](openspec/changes/plan-local-first-implementation/specs/) — требования и проверяемые сценарии.
- [design.md](openspec/changes/plan-local-first-implementation/design.md) — технический дизайн, зависимости и последовательность срезов.
- [tasks.md](openspec/changes/plan-local-first-implementation/tasks.md) — задачи реализации и способы их проверки.

## 1. Начало реализации

Завершите explore mode и вызовите команду:

```text
/opsx-apply plan-local-first-implementation
```

Явно ограничьте объём работы, чтобы ассистент не начал выполнять весь change:

```text
Реализуй только группу 1 из tasks.md — L01 «Запускаемые процессы».
Перед началом прочитай AGENTS.md и артефакты change.
Выполни проверки, отмечай задачи только после проверки результата.
После группы 1 остановись и сообщи результаты и блокеры.
```

Вместо slash-команды можно отправить в новой сессии обычный запрос:

```text
Начинаем реализацию, режим explore завершён.

Change: plan-local-first-implementation.
Выполни только группу 1 из
openspec/changes/plan-local-first-implementation/tasks.md.

Изучи AGENTS.md, proposal.md, design.md и относящиеся к группе спецификации.
Проверь git status, сохрани существующие изменения.
Реализуй задачи группы, выполни применимые проверки и обнови tasks.md.
После завершения группы остановись. К следующей группе не переходи.
```

Первая группа создаёт локальные процессы `web` и `worker`, конфигурацию, логи, корректную остановку, `/healthz` и основу метрик. Подготовка VPS не является условием её выполнения.

## 2. Продолжение в новой сессии

Меняйте номер группы в следующем шаблоне:

```text
Продолжи реализацию change plan-local-first-implementation.
Выполни только группу 2 из tasks.md.

Сначала проверь фактическое состояние кода, git status и выполнение зависимостей.
Прочитай AGENTS.md, design.md и соответствующие specs.
Не считай отмеченные задачи доказательством без проверки существующего результата.
После реализации запусти применимые проверки, обнови tasks.md и остановись.
```

Одна сессия — один законченный срез, а не обязательно один checkbox. Если группа слишком большая, ограничьте диапазон:

```text
Выполни только задачи 2.1–2.3. После их проверки остановись.
```

При блокере ассистент должен оставить незавершённые задачи открытыми и сообщить, что мешает продолжению. Начинать зависимую группу в обход блокера не следует.

## 3. Результат каждой сессии

После завершения среза в репозитории должны оставаться:

- рабочий код и актуальные сгенерированные файлы;
- выполненные применимые проверки;
- отметки завершённых задач в `tasks.md`;
- важные решения в дизайне либо ADR, если их нельзя восстановить из кода.

Итоговый ответ ассистента должен содержать:

1. Что реализовано и какие требования затронуты.
2. Какие файлы изменены.
3. Какие проверки выполнены и с каким результатом.
4. Какие блокеры или внешние проверки остались.

Приёмка на fake-провайдере должна явно отличаться от проверки реальной интеграции. Задача не считается завершённой только потому, что код написан.

## 4. Коммиты

Рекомендуется создавать коммит после каждого проверенного среза. Ассистент выполняет коммит только по явному запросу, например:

```text
Проверь diff и создай коммит завершённого среза.
```

Перед коммитом проверяются статус, diff и стиль последних сообщений. В коммит включаются только относящиеся к срезу изменения, без секретов и посторонней работы.

## 5. Команды OpenSpec

| Ситуация | Команда |
| --- | --- |
| Реализовать очередной срез | `/opsx-apply plan-local-first-implementation` с явным ограничением задач |
| Обсудить неоднозначность без реализации | `/opsx-explore` |
| Проверить соответствие реализации артефактам | `/opsx-verify plan-local-first-implementation` |
| Архивировать завершённый change | `/opsx-archive plan-local-first-implementation` после выполнения всего согласованного объёма |

Новый change на каждую сессию создавать не нужно. Продолжайте существующий, пока работа соответствует его спецификациям. Отдельный change нужен для самостоятельного изменения требований или функции за пределами текущего объёма.

Explore mode предназначен для исследования и обсуждения. Перед возвращением к реализации нужно явно завершить этот режим.

## 6. Как понимать статус готовности

Статус OpenSpec **planning complete** означает, что артефакты подготовлены. Он не подтверждает реализацию приложения.

Прогресс разработки определяется:

- состоянием задач в `tasks.md`;
- фактическим кодом;
- результатами тестов и проверок;
- доказательствами ручной и внешней приёмки.

Локальная готовность, готовность к внешнему пилоту и готовность к платному запуску — отдельные контрольные точки. Change не следует архивировать после одного среза или только на основании готовности документов.
