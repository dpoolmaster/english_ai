## Context

Мотивация и область изменения описаны в proposal.md. На момент планирования прикладного кода нет; есть ТЗ, AGENTS.md и локальный OpenSpec. Пользователь подтвердил локальную разработку в первую очередь, первый production-релиз из этапов 0 и 1 и минимальный admin auth в фундаменте. VPS общий, входящий трафик обслуживает Nginx; настройка размещения откладывается до внешнего пилота.

## Goals / Non-Goals

**Goals:**
- Реализовать контракты 20 capabilities из specs/ последовательностью проверяемых вертикальных срезов.
- Разделить локальную функциональную готовность, внешние проверки и готовность к платному запуску.
- Сохранить трассировку требований и выделить решения, которые должны быть приняты в дизайне будущего среза.

**Non-Goals:**
- Включать этапы 2–4 в первый релиз либо начинать кодирование, пока пользователь остаётся в explore mode.
- Угадывать внешние API, цены, юридические условия и параметры инфраструктуры.
- Пересматривать продуктовый объём ТЗ или объявлять этап завершённым без его приёмки.

## Decisions

### 1. Локальные контрольные точки вместо инфраструктурного старта

Подтверждено: доступность VPS и домена не является зависимостью локальных срезов. Полная приёмка этапа 0, включающая deployment и restore, закрывается до внешнего пилота, а не при первом локальном запуске.

Для первой реализации выбирается PostgreSQL в Compose, web/worker и Vite на хосте: это позволяет отлаживать процессы без пересборки контейнеров. Альтернатива — все процессы в Compose — сохраняется для проверки собранного приложения, но не обязательна в цикле редактирования. Версии закрепляются после проверки совместимости, а не по памяти модели.

```text
Browser --> Go web --> PostgreSQL <-- Go worker
   |           |
   |           +--> Templ / HTMX + embedded admin build
   |
   +--> Vite --> Go admin API

Local flows --> Fake providers
Verified adapters --> Real providers
Local MVP --> Deployment checks --> External pilot --> Paid launch
```

### 2. Спецификации и порядок реализации

Этот change содержит контракты всего первого релиза в specs/ и незавершённые задачи реализации в tasks.md. Выполняется один небольшой вертикальный срез за раз, после каждого — проверки и ревью. Не требуется заново создавать proposal для уже описанного поведения; новые продуктовые решения требуют согласованного изменения артефактов до кода.

Идентификаторы L01–L25 обозначают последовательность срезов, а capabilities — независимые контракты поведения. Матрица трассировки ниже связывает их. Наличие файлов или статус planning complete не означает выполнение tasks.md.

### 3. Порядок срезов первого релиза

#### Контрольная точка A: локальный фундамент

**L01 — Запускаемые процессы.** Основание: ТЗ 3, 9.3, 9.8. Проверить и закрепить версии Go/инструментов, создать web/worker, конфигурацию, JSON-логи, request ID, graceful shutdown и healthz. Приёмка: оба процесса собираются и корректно останавливаются; ошибки конфигурации не раскрывают секреты.

**L02 — База и генераторы.** Зависит от L01. Локальный PostgreSQL, pgxpool, migrate, sqlc, первая пара миграций и testcontainers. Приёмка: схема создаётся на чистой БД, обратная миграция проверена на тестовой БД, SQL генерируется, интеграционный тест использует настоящий PostgreSQL. Не создавать таблицы всех модулей заранее.

**L03 — Пользовательский веб-каркас.** Зависит от L01. Gin/Templ, локальные HTMX/Pico, layout, формы, ошибки 404/500, HTML-фрагменты, security headers. Приёмка: прямое открытие, обычная отправка формы, HTMX и ошибки форм работают, вывод экранируется. Источник: ТЗ 7.1, 9.1.

**L04 — Минимальный admin auth.** Зависит от L02–L03. Части FR-AUTH-2/3/6/7/8: argon2id, безопасный bootstrap, login/logout, серверные сессии, CSRF, роли и ограничения входа. Приёмка: проверены отказ входа, ротация, истечение, logout, отсутствие CSRF и роли. Это основа дальнейшего auth, а не отдельная временная система.

**L05 — Каркас админки.** Зависит от L04. Основа FR-ADM-1/2: Vue, OpenAPI 3.1, TS-типы, API, обработка 401/403, встроенная сборка и вложенные маршруты. Приёмка: вход администратора открывает защищённый API; SPA сама по себе не считается границей авторизации. Audit log подключается до первой бизнес-мутации.

**L06 — Воспроизводимость.** Развивается с L01, завершается после L05. README и единые команды запуска/миграций/генерации/сборки/тестов; CI, lint, vulnerability checks, проверка generated-кода. Приёмка: чистый клон запускается по инструкции; production build включает админку. Первый рубеж не требует VPS.

#### Контрольная точка B: первое завершённое занятие

**L07 — Регистрация, email и trial.** Зависит от L04–L06. FR-AUTH-1/2, FR-BIL-2/3: Mailer fake, River, подтверждение email, entitlements, единая проверка доступа. Приёмка: токен одноразовый, неподтверждённому пользователю занятия закрыты, конкурентное подтверждение выдаёт один trial. Проверка его окончания использует управляемые часы. Локальный просмотр письма не означает запись токенов в application logs.

**L08 — Ручной каталог и ревью.** Зависит от L05. FR-CUR-1/4, FR-EX-4/5, FR-ADM-1: навыки, зависимости без циклов, небольшой проверенный набор, схемы mcq/cloze_choice, draft/review/published, роли и аудит. Приёмка: упражнение создаётся, проходит ревью и становится доступным ученику только после публикации.

**L09 — Базовый цикл занятия.** Зависит от L07–L08. ТЗ 4.5, FR-EX-1/3: серверная очередь, проверка ответа, результат, следующий элемент, resume и finish. Приёмка: E2E от регистрации до итога; повтор ответа не создаёт вторую попытку; чужие занятия недоступны; answer_key не раскрывается до проверки. Промежуточная очередь не считается завершённым адаптивным planner.

Приёмка: эталонные ответы проверяют пробелы, апострофы, регистр, сокращения, опечатки и частичные баллы. LLM-fallback перевода добавляется в L20, а не теряется из MVP.

**L12 — Полный planner.** Зависит от L11. ТЗ 4.5: повторы, слабые места, prerequisites, goal weights, пропорции, новые навыки, порядок типов, адаптация после ошибок и content gaps. Приёмка: детерминизм при фиксированных данных/времени/seed; тесты лимитов, пустых категорий, размеров и возобновления.

**L13 — Онбординг и placement.** Зависит от L08, интеграция с L11–L12. FR-ONB-1/2: цель, время, timezone, старт A1 либо тест, Rasch/MAP, засев, повтор и recalibration. До UI выполнить симуляцию 1000 учеников. Приёмка: критерий точности ТЗ и максимум 25 вопросов; минимум 120 проверенных вопросов A1–B2 для MVP.

Приёмка: одноразовые токены, единые ответы, завершение сессий и ограничения проверены. Настоящий captcha и почта проверяются отдельно от fake.

**L16 — Данные аккаунта.** Зависит от L14, завершается с учётом таблиц всех готовых модулей до пилота. FR-AUTH-9, ТЗ 2.1/6: экспорт JSON, удаление, retention jobs и обезличивание платёжных записей. ### 4. Готовность к внешнему пилоту и запуску

После локального MVP: deployment на общий VPS с существующим Nginx, согласование с требованием Caddy в ТЗ, изолированные ресурсы, TLS, SSE без буферизации, production secrets, настоящая почта, метрики/алерты, encrypted backups и restore. Топология Nginx/Caddy уточняется задачей 25.1 после обследования: существующий Nginx не означает молчаливую замену стека ТЗ, решение фиксируется в дизайне до deployment.

Проверить k6: 150 одновременных сессий 10 минут, p95 страниц до 300 мс, проверки упражнения до 150 мс, ошибок не более 1%; первый токен тьютора p50 до 2 с. Проверить ASVS L1 и OAuth вручную. Реально восстановить backup с целями RTO 4 часа/RPO 24 часа. Завершить проверку оплаты, чека, возврата, доставки писем и доступности провайдеров.

До реальных пользователей: юридические условия обработки, документы/согласия, уведомление РКН и лицензии. До MVP-приёмки: минимум 700 опубликованных упражнений A1–A2, 120 placement questions и пилот 20–50 пользователей минимум 14 дней. Решение о платном запуске принимается после сбора метрик и устранения критичных замечаний.

### 6. Definition of Done среза

- Сценарии и ссылки на требования зафиксированы до кода; критичные негативные тесты auth/CSRF/payments/quotas написаны первыми.
- Миграции, серверная логика и UI образуют проверяемый сценарий; права и идемпотентность проверены на сервере.
- Generated-код обновлён, затем выполнены применимые тесты/проверки; в CI проверена его актуальность.
- Для PostgreSQL-сценариев используется настоящий PostgreSQL; provider adapters проверяются httptest; user flows — Playwright.
- Нет секретов/PII в логах; ошибки и деградация контролируемы; наблюдаемость добавлена.
- Сообщены файлы, команды, результаты, FR и внешние ограничения. Приёмка на fake явно отделена от реальной интеграции.
- При добавлении персональных данных обновлены export/delete/retention; при новой мутации админки — аудит.

### 7. Внешний путь и управление сроками

Подготовка программы, лицензий, юридических документов, магазина ЮKassa, LLM-доступов и почты идёт параллельно. Домен/VPS уже существуют; неизвестный статус остальных пунктов не считается отказом или выполнением. Их доступность выясняется к соответствующему срезу, не блокируя fake-разработку.

Оценка ТЗ 10–12 недель до запуска — ориентир, не обещание. Пересчитать план после контрольных точек A и B с учётом скорости, ревью контента и минимум 14 дней пилота. Задачи рассматриваются как работа одного разработчика с AI; автоматическое делегирование этим планом не предусматривается.

## Risks / Trade-offs

- [Календарный план без фактической скорости] → Оценивать срезы перед реализацией, пересматривать прогноз по контрольным точкам.
- [Спецификации приняты за реализованный MVP] → tasks.md содержит незавершённые задачи разработки; каждый checkbox закрывается только после указанной проверки.
- [Раздельная проверка и UPSERT квоты пропускают параллельные вызовы] → Отдельный дизайн конкурентности до внешних платных вызовов.
- [Fallback после первого SSE-токена дублирует ответ] → Отдельные сценарии частичного успеха, reconnect и списания в L23.
- [Rasch/SE не достигают критерия ТЗ] → Симуляция до UI; изменение формулы только через согласованное уточнение.
- [Правило JSONB противоречит примерам settings/quotas] → Решать на уровне конкретной схемы, документировать трактовку; не копировать SQL-примеры механически.
- [Функциональный раздел и этапы коучинга расходятся] → Спецификация coaching-dashboard явно закрепляет FR-COA-1/3 в MVP и FR-COA-2/4 на этапе 3 по разделу 11.
- [Флаги публикации меняются внутри активного занятия] → В L17 определить проверку доступности и замену элемента, не ограничиваться фильтром при сборке.
- [Локальные cookie/CSRF отличаются от production] → Явная конфигурация среды, тесты production-политик, решение HTTP/HTTPS localhost в L04.
- [Контент становится последним блокером] → Ранний ручной каталог и параллельная подготовка программы; объём принимается по опубликованному, а не сгенерированному контенту.

## Migration Plan

Текущая запись артефактов не меняет приложение и БД. Будущая реализация расширяет схему отдельными up/down парами по готовности срезов: auth → catalog → learning → billing/quota → tutor/content → coaching/operations. Номера назначаются по фактическому порядку, примеры SQL ТЗ не считаются готовыми миграциями. River-миграции поставляются совместимыми SQL-файлами. Перед каждым переходом проверяются fresh DB и upgrade с предыдущего состояния; down выполняется только на одноразовой тестовой базе.

Перед пилотом: резервная копия, расширяющие миграции, новый образ, health smoke, затем переключение трафика. Откат приложения использует предыдущий тег на совместимой расширенной схеме, без автоматического destructive down. Очистка колонок — отдельная более поздняя миграция. Этот change архивируется только после выполнения задач и приёмки, не после одного создания документов.

## Implementation Architecture

### Модули и данные

Один Go-модуль, web/worker — composition roots. Domain services принимают интерфейсы, clock и randomness; Gin/Templ, pgx/sqlc и адаптеры не протекают в алгоритмы. platform содержит config/logger/db/httpx/clock, но не становится общим бизнес-модулем. LLM/speech/billing provider не импортируют учебные модули.

Таблицы добавляются со сценарием. Auth: users, identities, sessions, email_tokens, auth_attempts. Каталог: skills/prereqs, vocab/examples, exercises, placement_items, error_types, prompt_versions. Learning: lessons/items, attempts, skill/vocab states, review_log, placement sessions, error_events. Billing: plans/orders/payments/entitlements, durable webhook inbox и финансовые операции. Quota: counters плюс журнал операций и резервов. Tutor/content: conversations/messages, generation jobs/проверки. Operations: reports, notifications, audit_log, settings, events и provider calls.

Уникальные ограничения обеспечивают sid hash, identity(provider,subject), нормализованный email, один trial на user, одну attempt на item, один логический review/analysis на source, одну выдачу доступа на order, provider payment, webhook/operation keys и notification dedupe. Nullable FK и удаление учётных записей проектируются вместе с обезличиванием, а не оставляются до последнего FK-конфликта. JSONB сохраняется для полиморфных payload/result; исключения ТЗ (settings/quotas/goal weights) оформляются явным ADR перед миграцией. Денежный учёт платежей целочисленный; дробная стоимость API — decimal по примеру ТЗ, не float.

### Транзакции и конкурентность

- Answer: lock lesson/item → проверить владельца/доступ/состояние → принять первый ответ → attempt/result/error/review/adaptation → commit. Повтор читает сохранённый результат. Внешний LLM перевода выполняется через отдельную durable operation вне открытой SQL-транзакции; окончательная фиксация снова блокирует item.
- Start lesson: сериализовать выбор новых навыков для user/day, сохранить выбранный seed/время/очередь и назначения новых навыков атомарно. Проверка каталога повторяется перед показом; flagged item заменяется без штрафа.
- Graph edits: изменение зависимостей сериализуется в рамках графа и проверяет цикл на согласованном снимке; проверки только на клиенте недостаточно.
- Trial: confirmation и unique trial фиксируются одной транзакцией. Payment: inbox → проверка API вне длинной транзакции → lock order и user access → сверка суммы/RUB/metadata → payment/order/entitlement + письмо в River → commit. Разные оплаченные заказы одного user сериализуют продление.
- Refund: durable operation с idempotency key создаётся до внешнего вызова; retry сверяет состояние, завершает audit/access transition. Внешний эффект нельзя откатить SQL rollback, поэтому задача reconciliation обязательна.
- Notifications и product events используют ключ источника, не только best-effort проверку существования перед INSERT.

### Резервирование квот

Проверка и последующее списание разделяются durable quota operation: key/user/metric/period/amount/state/result reference и резерв. Под блокировкой bucket проверяется consumed + active reserved + requested <= limit; резерв фиксируется до API. Сетевой вызов выполняется без удержания DB connection/lock. Успешный доменный результат и перевод резерва в consumed с UPSERT фиксируются одной транзакцией; failure освобождает резерв идемпотентно.

Операция закрепляет период при допуске. Для периодов квот выбирается UTC как согласованный с хранением usage default; timezone ученика используется для напоминаний и учебных дней. Это техническая трактовка неуточнённой границы ТЗ, которую нужно явно показать в ADR и интерфейсе лимитов. Дневной лимит новых навыков и streak используют timezone ученика.

Recovery не освобождает резерв только из-за обрыва браузера: учитывает deadline, lease worker и сохранённый результат. После исчерпания предельного срока незавершённая генерация помечается failed, квота освобождается; неизвестная стоимость отмечается неизвестной, а не нулевой. Полностью гарантировать exactly-once вызов неидемпотентного LLM после падения нельзя: гарантируется однократный доменный результат/списание, неоднозначная попытка не повторяется незаметно. Provider attempt journal отделён от пользовательской квоты.

### SSE и LLM

POST сообщения создаёт уникальный user turn/response operation с квотой. GET stream только подписывается и не инициирует платную генерацию. Генерация идёт с общим 20-секундным deadline; события и состояние связаны с response id. Reconnect получает сохранённый текст/актуальное состояние, а не запускает Complete/Stream заново. Один активный ход сериализуется на conversation; токены экранируются до выдачи, Markdown не рендерится.

До первого токена разрешён fallback в оставшемся deadline. После первого токена не склеиваем ответ другой модели: при окончательном обрыве сохраняется partial/failed, выдаётся error, квота не потребляется. Завершённый ответ и quota success коммитятся до done. При потере done reconnect возвращает завершённый результат. Резюме истории тоже считается внешним вызовом с purpose/стоимостью и приватным контекстом. Analysis job ставится идемпотентно по user message.

### Детерминированные алгоритмы

Planner использует стабильные tie-break по id/code, injected clock и seeded RNG. Для числа заданий применяется округление до ближайшего целого с последующим clamp 6–26; для долей — largest remainder со стабильным приоритетом review/weak/new. Пустая доля передаётся следующей доступной категории в цикле review → weak → new → review. Это явно документируемые трактовки незаданных правил округления, не замена пропорций ТЗ. При невозможной комбинации порядка/достаточности content gap важнее выдачи непроверенного контента.

Placement сохраняет version/config snapshot, выбранные вопросы и ответы; выбор без повторов и стабильные ties, ограничение баланса на коротком префиксе применяется по достижимости, финальная доля проверяется. «Не знаю» обрабатывается отдельно от угаданного варианта. Формулы ТЗ сначала проверяются симуляцией; если SE и guessing-модель не обеспечивают приёмку, дальнейшее изменение согласуется до реализации альтернативного алгоритма. FSRS оборачивается с фиксированным временем, не переписывается самостоятельно.

### HTTP, admin и локальная безопасность

Templ Render, обычный POST redirect и HX-Redirect/fragment выбираются по типу запроса. CSRF применяется и до авторизации (login/register/reset), затем привязывается к сессии; webhook имеет собственную защиту. Same-origin Vite proxy направляет admin API в web, чтобы не ослаблять CORS/CSRF для разработки. Production всегда требует Secure cookie; локальный режим явно конфигурируется и не допускается в production. Создание admin — интерактивная/контролируемая команда без секрета в аргументах shell history, повтор не повышает роль существующего аккаунта молча.

Rate limits хранятся в PostgreSQL с атомарным допуском и очисткой, не в локальной map. Admin API применяет roles до handler, owner checks внутри сервисов, audit в транзакции мутации. OpenAPI является источником TS-типов. SPA fallback не перехватывает API 404; assets embedded в production, Vite используется только для разработки.

### Проверки и наблюдаемость

Unit: normalizer/checkers, FSRS, planner, placement simulation, order transitions, quota arithmetic. PostgreSQL integration: migrations, auth/CSRF/roles, concurrent answers/trials/payments/quotas, retries River, deletion. Adapter httptest: status, 429/5xx, timeout/cancel, schema repair, redacted errors. Playwright: register/verify/onboard/placement/lesson/fake payment/chat, admin review и denial reviewer. Evals не заменяются unit-тестом наличия строк в промпте.

Генерация Templ/sqlc/OpenAPI types предшествует tests/vet/build. CI проверяет generated diff, frontend build, coverage, lint и vulnerabilities. Метрики не используют тексты/email и не включают user_id как бесконтрольно высококардинальную метку. SQL-планы крупных выборок проверяются EXPLAIN; pgxpool по ТЗ до 20 web/10 worker, без транзакций через сетевые вызовы.
