## Purpose

Обеспечить воспроизводимый локальный запуск сервиса и фоновых процессов, проверяемую схему данных и безопасную эксплуатационную основу без зависимости от VPS.

## ADDED Requirements

### Requirement: Reproducible local environment
Система MUST запускаться с чистого клона по README без внешних платных аккаунтов, используя локальную БД и fake-провайдеры. Версии инструментов и зависимостей MUST быть закреплены. Основание: ТЗ 3, 9.6–9.8.

#### Scenario: Clean checkout
- **WHEN** разработчик выполняет документированные команды на поддерживаемом окружении
- **THEN** создаётся схема БД, запускаются web и worker, доступны пользовательская страница и сборка админки.

### Requirement: Configuration and lifecycle
Процессы MUST валидировать конфигурацию до обслуживания, получать секреты только из окружения, корректно завершаться и предоставлять публичный healthz без секретов. Метрики MUST быть доступны только внутренне. Основание: ТЗ 3.3, 9.3–9.4.

#### Scenario: Invalid configuration
- **WHEN** отсутствует обязательный параметр или задан неизвестный провайдер
- **THEN** запуск завершается с диагностикой имени параметра без раскрытия его секретного значения.

#### Scenario: Shutdown and health
- **WHEN** процесс получает сигнал остановки
- **THEN** прекращается приём новой работы, текущая работа завершается либо отменяется в пределах настроенного срока, незавершённые задачи остаются восстанавливаемыми.

### Requirement: Versioned persistent state
Изменения схемы MUST иметь up/down миграции и сохранять согласованность ограничений. Повторный запуск миграций MUST не повторять применённые изменения. Продуктовые timestamps хранятся в UTC, суммы — в копейках. Основание: ТЗ 6, 9.3.

#### Scenario: Fresh and existing database
- **WHEN** миграции запускаются на пустой и затем повторно на актуальной базе
- **THEN** создаётся одна и та же актуальная схема без потери существующих данных и повторных seed-операций.

### Requirement: Recoverable background work
Фоновые операции MUST иметь ограниченные повторы, идемпотентные эффекты и диагностику ошибок без персонального содержимого; постановка связанной с мутацией задачи MUST быть транзакционной. Основание: ТЗ 8.4.

#### Scenario: Worker restarts
- **WHEN** worker падает после фиксации бизнес-изменения и перезапускается
- **THEN** задача не теряется, повтор не дублирует подтверждённый бизнес-эффект.
