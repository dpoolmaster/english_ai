# Техническое задание: веб-сервис изучения английского языка с ИИ-тьютором

Версия 1.0 · 29 октября 2026 · Статус: готово к реализации, на согласование

## 1. Общие сведения

### 1.1. Цель проекта

Платный веб-сервис, который заменяет репетитора по английскому для уровней A1–B2 (CEFR) для русскоязычных взрослых. Сервис не «чат с нейросетью», а система из пяти частей: модель знаний ученика, детерминированный планировщик занятий, проверенный каталог упражнений, ИИ-тьютор для живой практики и коучинг (напоминания, статистика, возвращение после пропусков).

Критерий успеха продукта: ученик за 3 месяца регулярных занятий поднимается на подуровень CEFR по независимому тесту и продолжает заниматься без принуждения. Технические метрики: см. раздел 10.

### 1.2. Аудитория

- Взрослые 18+ (условие оферты; снимает вопросы согласия законных представителей по 152-ФЗ).
- Русскоязычные, оплата в рублях, интерфейс на русском.
- Объяснения на русском для A1–B1; на B2 — по умолчанию английский, русский по кнопке.
- Устройства: смартфон и десктоп, адаптивный веб (PWA-манифест, без нативных приложений).
- Нагрузка: до 3000 зарегистрированных пользователей, пик до 150 одновременных сессий.

### 1.3. Границы проекта

**В объёме:** регистрация и вход; диагностика уровня; программа A1–B2 как граф навыков; упражнения с автопроверкой; интервальные повторения; текстовый тьютор; проверка письма; голосовой тьютор и упражнения «прочитай вслух»; коучинг; оплата периодов доступа; админка; жалобы на задания.

**Вне объёма:** нативные мобильные приложения; автопродление подписок; живые преподаватели; видеоуроки; соцфункции (рейтинги, друзья); сертификаты; уровни A0 и C1+; собственная оценка произношения на уровне фонем (только через внешний API, этап 4).

### 1.4. Принятые решения

| Область | Решение |
| --- | --- |
| Язык и веб-фреймворк | Go (актуальная стабильная версия), Gin |
| БД | PostgreSQL 16+, драйвер pgx v5, генерация запросов sqlc, миграции golang-migrate |
| Очередь задач | River (на Postgres), без Redis и брокеров |
| Пользовательский фронт | Templ + HTMX 2 + Pico.css v2 + собственный app.css; JS только в «островах» (запись голоса, таймеры) |
| Админка | Vue 3 + Vite + TypeScript + Pinia + Vue Router + PrimeVue + TanStack Query; статика встраивается в бинарник (`go:embed`), отдаётся с `/admin` |
| Аутентификация | Email + пароль (argon2id), OAuth2: Яндекс ID и VK ID; собственные серверные сессии в Postgres |
| LLM | Open-weight модели (Qwen, DeepSeek и др.) через интерфейс `LLM`; конкретный провайдер подставляется конфигом |
| Распознавание речи (ASR) | Yandex SpeechKit через интерфейс `Transcriber` |
| Синтез речи (TTS) | Yandex SpeechKit через интерфейс `Synthesizer`; браузерный `speechSynthesis` как запасной вариант для отдельных слов |
| Оценка произношения | MVP: по результату ASR. Этап 4: внешний API через интерфейс `PronunciationAssessor` |
| Платежи | ЮKassa (самозанятый), предоплата периодов 1/3/12 мес., без автопродления; интерфейс `PaymentProvider` |
| Пробный период | 3 дня, значение в конфиге |
| Хостинг | FirstVDS (РФ), Docker Compose, Caddy |
| Команда | 1 разработчик + AI-ассистент |

### 1.5. Ограничения и допущения

1. Один разработчик. Всё, что можно не писать, не пишем: меньше сервисов, меньше зависимостей, меньше своих «велосипедов» вне ядра.
2. Нет GPU и мощных серверов: всё тяжёлое (LLM, ASR, TTS) только через внешние API по интерфейсам.
3. Все внешние сервисы заменяемы через интерфейсы (раздел 5). Бизнес-логика не знает имён провайдеров.
4. Контент (упражнения, объяснения) генерируется заранее пакетно и проходит ревью человека. Генерация «на лету» только для тьютора, проверки письма и персональных примеров.
5. Цены, лимиты и параметры провайдеров, помеченные «уточнить», проверяются в момент реализации по документации провайдера, а не берутся из этого ТЗ.

### 1.6. Глоссарий

- **CEFR** — шкала уровней A1, A2, B1, B2.
- **Навык (skill)** — узел программы: грамматическая тема, лексический набор или фонетическая тема.
- **Упражнение (exercise)** — единица практики, привязанная к навыку.
- **Сессия занятия (lesson)** — очередь упражнений на 10–15 минут, собранная планировщиком.
- **FSRS** — алгоритм интервальных повторений (Free Spaced Repetition Scheduler).
- **Recast** — тьютор повторяет фразу ученика в исправленном виде, не прерывая разговор лекцией.
- **Entitlement** — право доступа: trial или оплаченный период.

## 2. Юридические и регуляторные требования

Раздел информационный: обязательно согласовать с юристом или бухгалтером до запуска.

### 2.1. Персональные данные (152-ФЗ)

1. Данные пользователей хранятся только на серверах в РФ (FirstVDS, ЦОД в РФ). Резервные копии тоже в РФ.
2. До начала обработки подать уведомление об обработке персональных данных в Роскомнадзор (оператор — самозанятый как физическое лицо).
3. Документы на сайте: политика обработки персональных данных, согласие на обработку (чекбокс при регистрации, не предустановленный), публичная оферта, правила возврата, контакты оператора (ФИО, ИНН, email).
4. Минимизация: собираем email, хэш пароля, идентификаторы OAuth, прогресс обучения. Телефон, дату рождения, адрес не собираем.
5. Удаление аккаунта: пользователь удаляет данные сам в кабинете; в течение 30 дней удаляются персональные данные, обезличиваются платёжные записи (хранятся по требованиям учёта).
6. Голосовые записи пользователя не сохраняются: обрабатываются в памяти, отправляются в ASR и выбрасываются. Исключение только по явному согласию для разбора ошибок (в MVP не реализуется).
7. Передача данных за рубеж (например, при подключении зарубежного API оценки произношения на этапе 4) допустима только после отдельной проверки юристом: уведомление РКН о трансграничной передаче, отдельное согласие пользователя, передача без идентификаторов пользователя.
8. В запросах к LLM, ASR и TTS не передаются email, имя и иные идентификаторы. Передаётся только обезличенный учебный контекст.

### 2.2. Налоги и приём платежей

1. Статус самозанятого (НПД): учитывать годовой лимит дохода (на момент составления ТЗ 2,4 млн ₽, уточнить актуальное значение) и невозможность найма сотрудников. При приближении к лимиту нужен переход на ИП. Для этого платежи изолированы за интерфейсом `PaymentProvider`, а юрлицо провайдера задаётся конфигурацией, без изменений в бизнес-логике.
2. Чек на каждый платёж формируется автоматически в момент получения оплаты. Реализация через ЮKassa; условия подключения самозанятых и перечень доступных способов оплаты уточнить при регистрации магазина.
3. Возвраты: оформляются в админке через API ЮKassa; правила возврата за неиспользованную часть периода зафиксировать в оферте.
4. Автопродление не используется, поэтому требования к рекуррентным платежам и отдельному управлению подпиской не применяются. Но сервис присылает напоминания об окончании доступа (раздел 4.10).

### 2.3. Прочее

- Cookies: только технические (сессия, CSRF). Баннер не нужен, но уведомление в политике обязательно.
- Контент словарей: источники частотных списков и CEFR-разметки выбираются с проверкой лицензии на коммерческое использование (кандидаты: CEFR-J Wordlist и открытые корпусные списки; материалы Cambridge EGP/EVP и Oxford 3000/5000 использовать только после изучения условий лицензии). Контент, сгенерированный LLM, проходит ревью и не копирует защищённые тексты.

## 3. Архитектура

### 3.1. Принципы

1. **Модульный монолит.** Один репозиторий, один Go-модуль, два исполняемых файла: `web` и `worker`.
2. **Postgres — единственное хранилище состояния:** данные, очередь (River), сессии, кэш-таблицы, счётчики, `LISTEN/NOTIFY`.
3. **Все внешние сервисы за интерфейсами**, реализации выбираются конфигом: LLM, ASR, TTS, оценка произношения, платежи, почта, файловое хранилище.
4. **Детерминированное ядро.** Планировщик, проверка закрытых упражнений, FSRS, квоты — обычный Go-код без LLM.
5. **Сервер — источник истины.** Состояние занятия и диалога хранится на сервере, браузер только отображает HTML-фрагменты.
6. **Идемпотентность** вебхуков платежей, задач очереди и повторных отправок ответов.
7. **Наблюдаемость по умолчанию:** каждый вызов LLM, ASR и TTS пишет стоимость и задержку в таблицу.

### 3.2. Компоненты и процессы

```
Браузер ── HTMX / SSE ───────────────► web (Gin)
   │                                       │ ├─► Postgres (данные, сессии, очередь River)
   │ POST аудио (PCM) ─────────────────────┤ ├─► LLM-провайдер (open-weight, OpenAI-совместимый API)
   │                                       │ ├─► Yandex SpeechKit (ASR, TTS)
Vue-админка ── JSON API /admin/api ──────►│ └─► ЮKassa (создание платежа)
                                           │
ЮKassa ── webhook ───────────────────────►│
                                           ▼
                                  worker (River): генерация контента, пересчёт
                                  модели ученика, письма, напоминания, очистка
```

- **web** — HTML (Templ), JSON API админки, вебхуки, SSE, приём аудио, `/healthz`, `/metrics` (только внутренняя сеть).
- **worker** — фоновые задачи (раздел 8 и 4.10). Может работать в том же контейнере, пока нагрузка мала, но запускается как отдельный процесс из того же кода.
- **Caddy** — TLS-терминация, сжатие, статика медиа, проксирование в `web`.

## 4. Функциональные требования

Нумерация требований: FR-модуль-номер. Всё помеченное «этап N» входит в соответствующий релиз (раздел 11).

### 4.1. Аутентификация и аккаунт

- **FR-AUTH-1. Регистрация по email и паролю.** Email приводится к нижнему регистру и проверяется на формат. Пароль не короче 10 символов, проверяется по локальному списку популярных паролей; требований к спецсимволам нет. Подтверждение email обязательно: письмо со ссылкой, токен 32 байта из crypto/rand, в БД хранится только SHA-256 хэш, срок жизни 24 часа, одноразовый. До подтверждения нельзя начать trial и занятия.
- **FR-AUTH-2. Хэширование паролей.** argon2id, параметры по умолчанию: память 19456 КиБ, 2 прохода, 1 поток, соль 16 байт, ключ 32 байта, хранение в стандартном PHC-формате. Параметры в конфиге; при входе хэш с устаревшими параметрами пересчитывается. Одновременных вычислений хэша не больше 4 (семафор), чтобы вход нельзя было использовать для исчерпания памяти.
- **FR-AUTH-3. Вход.** Единый текст ошибки «неверный email или пароль». Лимит 5 неудачных попыток за 15 минут на пару (IP, email), дальше показывается Yandex SmartCaptcha. Постоянной блокировки аккаунта нет.
- **FR-AUTH-4. OAuth2: Яндекс ID и VK ID.** Authorization Code с PKCE, параметр state одноразовый и привязан к cookie. Запрашиваются минимальные права (идентификатор и email). Таблица oauth\_identities (provider, subject) связывает аккаунт с провайдером. Правила привязки:
  1. Есть identity — вход в связанный аккаунт.
  2. Identity нет, email пришёл и подтверждён провайдером (Яндекс), аккаунт с таким email существует — привязка только после ввода пароля этого аккаунта или перехода по ссылке из письма.
  3. Email не пришёл или не подтверждён провайдером (возможно у VK ID) — форма ввода email и подтверждение письмом, только затем создание или привязка.
  4. Автоматическая привязка по неподтверждённому email запрещена (риск захвата аккаунта).
- **FR-AUTH-5. Сброс пароля.** Письмо со ссылкой, токен живёт 1 час, одноразовый, после смены пароля все сессии пользователя завершаются. Ответ на запрос одинаков для существующего и несуществующего email.
- **FR-AUTH-6. Сессии.** Собственная таблица sessions. Cookie sid: 32 случайных байта в base64url, HttpOnly, Secure, SameSite=Lax. В БД хранится SHA-256 токена. Срок 30 дней со скользящим продлением (не чаще раза в сутки), смена идентификатора при входе и смене пароля. В профиле список устройств (user-agent, последняя активность) и кнопка «выйти везде».
- **FR-AUTH-7. CSRF.** Токен привязан к сессии, передаётся в hx-headers на теге body и в скрытом поле обычных форм, проверяется на всех не-GET запросах. Вебхуки исключены и защищены собственной проверкой.
- **FR-AUTH-8. Роли.** user, reviewer, admin. Проверка роли на сервере в middleware для каждого защищённого маршрута, скрытия кнопок недостаточно.
- **FR-AUTH-9. Аккаунт.** Смена email (с подтверждением нового адреса) и пароля, экспорт данных в JSON, удаление аккаунта по правилам из 2.1.

**Приёмка:** все сценарии покрыты интеграционными тестами; ручная проверка захвата аккаунта через OAuth (правило 4) пройдена; при 100 одновременных логинах память процесса не превышает заданный бюджет.

### 4.2. Онбординг и диагностика уровня

**FR-ONB-1.** После подтверждения email: выбор цели (работа, переезд, путешествия, экзамен, для себя), времени в день (5/10/15/20 минут), часового пояса (определяется браузером, правится), времени напоминаний. Затем выбор: пройти тест уровня или начать с нуля (стартовый уровень A1, тест пропускается).

**FR-ONB-2. Адаптивный тест.** Цель — определить уровень за 10–15 минут и засеять карту знаний.

- Банк вопросов placement\_items: не меньше 120 вопросов (по 30 на уровень), типы — грамматика, лексика, чтение; отдельный от банка уроков, чтобы ученик не видел те же задания на занятиях.
- Модель: Rasch с фиксированным параметром угадывания c = 1/k (k — число вариантов): P = c + (1−c)·σ(θ−b). Стартовое θ = −0,5.
- Выбор следующего вопроса: ближайший по сложности (минимум модуля разности b и θ) среди не показанных, при условии, что доля каждого типа не ниже 20%.
- Оценка θ — MAP-оценка с нормальным априором N(0; 1,5²) после каждого ответа (несколько итераций Ньютона). Стандартная ошибка SE = 1 / корень из суммы p(1−p).
- Остановка: не менее 12 вопросов и SE < 0,4, либо 25 вопросов.
- Начальная сложность вопроса b берётся из метки уровня (A1 = −2, A2 = −1, B1 = +0,3, B2 = +1,5) и правится экспертом. Задача recalibrate\_items в worker пересчитывает b по накопленным ответам, когда на вопрос набралось не менее 200 ответов.
- Кнопка «не знаю» считается неверным ответом без угадывания.
- Пороги перевода θ в CEFR хранятся в конфиге; начальные: A1 < −1,5; A2 от −1,5 до −0,3; B1 от −0,3 до +0,9; B2 ≥ +0,9.
- Результат: уровень, сильные и слабые разделы, предложение цели. Засев user\_skill\_state по правилам: навыки ниже уровня — стартовая вероятность освоения 0,85; на уровне — 0,4; выше — 0,05 (значения в конфиге).
- Повторный тест доступен раз в 30 дней и обновляет карту, не стирая историю.

**Приёмка:** на симуляции из 1000 виртуальных учеников с известным θ средняя абсолютная ошибка оценки уровня не больше половины уровня CEFR; тест укладывается в 25 вопросов.

### 4.3. Программа (граф навыков)

- **FR-CUR-1.** Навык (skills): код, название, вид (grammar, vocab\_set, pronunciation, function), уровень CEFR, описание «умею» на русском, объяснение в Markdown (до 250 слов, 2–4 примера EN + RU), порядок. Зависимости (skill\_prereqs) образуют ациклический граф; админка проверяет отсутствие циклов при сохранении.
- **FR-CUR-2.** Ориентиры по объёму полной программы: грамматика около 145 навыков (A1 ≈ 30, A2 ≈ 35, B1 ≈ 40, B2 ≈ 40); лексика около 4000–5000 слов с разметкой уровня и русским переводом; на каждый навык 10–15 упражнений разных типов.
- **FR-CUR-3.** Объём MVP: A1 и A2 полностью, тест уровня на все четыре уровня. B1 и B2 добавляются волнами на этапе 3 без изменения кода (только контент).
- **FR-CUR-4.** Цель ученика влияет на веса навыков в планировщике (goal\_weights: например, для цели «работа» выше вес деловой лексики и функций).

### 4.4. Упражнения

**FR-EX-1. Типы упражнений** (проверка выполняется Go-кодом, без LLM):

| cloze\_choice | пропуск, варианты | совпадение id | 1 |

**FR-EX-2. Нормализация ответов:** обрезка пробелов, схлопывание повторных пробелов, регистр (флаг на упражнении), унификация апострофов, игнорирование завершающей пунктуации, опциональная эквивалентность сокращений (I'm = I am, флаг), допуск опечатки в 1 символ для слов длиннее 4 букв (ответ засчитывается, показывается подсказка; поведение настраивается).

**FR-EX-3. Обратная связь:** после ответа показываются результат, правильный вариант, готовое объяснение explanation\_ru из карточки упражнения (не генерируется на лету), кнопки «показать правило» и «пожаловаться». У неверных вариантов может быть тег error\_type, который сразу пишется в error\_events.

**FR-EX-4. Формат данных.** payload и answer\_key — JSON с обязательным schema\_version. Схемы JSON хранятся в /docs/schemas, валидируются при сохранении и публикации. Пример (условная запись для читаемости, в БД это JSON):

```yaml

type: cloze_choice
prompt: She ___ to work by bus every day.
options:
  - {id: a, text: go, error_type: subject_verb_agreement}
  - {id: b, text: goes}
  - {id: c, text: going, error_type: verb_form}
answer_key: {correct: b}
explanation_ru: С she, he, it в Present Simple к глаголу добавляется -s.
```

**FR-EX-5.** Статусы: draft → review → published → flagged / archived. Ученику показываются только published.

### 4.5. Планировщик занятий

Детерминированный Go-код без LLM. Метод Planner.BuildLesson(user, targetMinutes).

1. Кандидаты **повторов**: due\_at <= now в user\_skill\_state и user\_vocab\_state, по убыванию просрочки.
2. Кандидаты **слабых мест**: навыки из топ-3 типов ошибок за последние 14 дней (error\_events) и навыки с низкой вероятностью освоения.
3. Кандидаты **нового**: навыки, у которых все prerequisites освоены (вероятность ≥ 0,7), отсортированные по весу цели ученика и порядку программы. Не больше 1 нового навыка в занятие и 2 в день (конфиг).
4. Пропорции 50/25/25 (повторы / слабые места / новое) настраиваются; если категория пуста, долю получает соседняя.
5. Размер занятия: items = targetMinutes × 1,3 (около 45 секунд на задание), от 6 до 26.
6. Порядок: новый навык начинается с карточки объяснения, затем 3 лёгких задания; остальное перемешивается; не более 3 подряд заданий одного типа.
7. Адаптация внутри занятия: после двух ошибок подряд по одному навыку в очередь вставляется одно более лёгкое задание и ссылка на правило.
8. Если опубликованных упражнений для выбранного навыка не хватает, он пропускается и в логе появляется событие planner.content\_gap (видно в админке).
9. Состояние занятия (lessons, lesson\_items) хранится на сервере; возобновление после обрыва — с первого неотвеченного задания.
10. Итоговый экран: точность, время, новые слова, серия дней, ближайшие повторы.

**Приёмка:** юнит-тесты на пропорции, зависимости, лимиты и пустые категории; один и тот же набор данных даёт одну и ту же очередь (детерминизм при фиксированном seed).

### 4.6. Интервальные повторения (FSRS)

- **FR-SRS-1.** Два типа состояния: user\_skill\_state (грамматика, функции) и user\_vocab\_state (слова). Поля FSRS: stability, difficulty, state, reps, lapses, due\_at, last\_review\_at.
- **FR-SRS-2.** Соответствие ответа и оценки: верно и быстро — Easy или Good (порог времени по типу упражнения); верно, но медленно или с подсказкой — Hard; неверно — Again. Для карточек оценка выставляется самим учеником.
- **FR-SRS-3.** Каждый ответ пишет запись в review\_log (достаточно для последующей оптимизации параметров FSRS на реальных данных).
- **FR-SRS-4.** Показатель освоения навыка для UI и планировщика — вероятность вспоминания (retrievability) на текущий момент, вычисляется на лету.
- **FR-SRS-5.** Повтор слова всегда в новом контексте: для слова хранится 3–5 проверенных примеров, показывается тот, который ученик видел давно.

### 4.7. Текстовый ИИ-тьютор

**Режимы:** свободный разговор по теме, ролевые сценарии (каталог tutor\_scenarios, около 20 на старте: кафе, аэропорт, собеседование, small talk и т.д.), «разберём мою ошибку» (из error\_events).

**FR-TUT-1. Поведение** (закрепляется системным промптом, версия хранится в БД):

- уровень речи тьютора = уровень ученика плюс половина ступени; реплики короткие (до 60 слов для A1–A2, до 100 для B1–B2), один вопрос за ход;
- исправления через recast (повтор фразы в правильном виде), без перебивания лекцией; подробный разбор только в конце диалога;
- мягко уводит разговор к слабым местам из профиля ученика и использует его недавние слова;
- на A1–A2 при затруднении ученика допустимы русские пояснения; на B1+ только по кнопке;
- кнопки «подсказка» (три варианта ответа) и «переведи».

**FR-TUT-2. Сборка контекста** (бюджет задаётся в конфиге): системный промпт + снимок профиля (до 400 токенов: уровень, цель, 5 главных типов ошибок, 20 недавних слов) + сценарий + последние сообщения (не более 12 и не более 2000 токенов) + сжатое резюме более ранней части диалога. В запрос не попадают email, имя и иные идентификаторы.

**FR-TUT-3. Анализ ошибок.** После каждого сообщения ученика асинхронная задача просит модель вернуть строгий JSON: список ошибок (тип из справочника error\_types, фрагмент, исправление, пояснение на русском). Результат валидируется, пишется в error\_events и показывается в панели «Разбор» после завершения диалога. При невалидном JSON — один повтор, затем пропуск без ошибки для ученика.

**FR-TUT-4. Лимиты:** сообщение ученика до 500 символов, диалог до 40 реплик, дневные квоты по тарифу (4.11). Проверка квоты до вызова модели, списание после успешного ответа.

**FR-TUT-5. Стриминг.** Ответ идёт по SSE: события token, done, error. Токены экранируются на сервере, разметка Markdown не рендерится (только переносы строк), чтобы исключить XSS из вывода модели.

**FR-TUT-6. Защита.** Текст ученика передаётся в отдельном блоке с разделителями; системный промпт запрещает менять роль и раскрывать инструкции; вывод проверяется на нерелевантные для обучения темы по простым правилам (длина, язык, стоп-список); при токсичном вводе тьютор отвечает отказом и возвращается к теме. Дисклеймер «ИИ может ошибаться», кнопка «Неверно» на каждой реплике (4.13).

**FR-TUT-7. Отказоустойчивость.** Таймаут генерации 20 секунд; при ошибке или таймауте — запрос к резервному провайдеру из цепочки (раздел 5); если и он недоступен, ученик видит понятное сообщение, квота не списывается.

### 4.8. Проверка письма (этап 3)

- **FR-WR-1.** Задания по уровням (например, 3–5 предложений о выходных для A2, 80–120 слов для B1), текст до 1500 символов.
- **FR-WR-2.** Асинхронная задача: модель возвращает строгий JSON — исправленный текст, список ошибок с типами, оценки по критериям (задача, грамматика, лексика, связность) от 0 до 5 по рубрике CEFR и три совета. Разница между исходным и исправленным текстом (diff по словам) строится в Go, а не моделью.
- **FR-WR-3.** Ошибки пишутся в error\_events с source=writing. Результат появляется в интерфейсе через HTMX-опрос или SSE.
- **FR-WR-4.** Калибровка: набор из 50 эталонных текстов с экспертной оценкой; перед выкладкой новой версии промпта прогон и сравнение (допустимое отклонение 0,5 балла в среднем). Это защита от подхалимства модели.
- **FR-WR-5.** Справочник error\_types: article, preposition, tense, aspect, subject\_verb\_agreement, word\_order, plural, countability, modal, conditional, comparative, gerund\_infinitive, pronoun, phrasal\_verb, collocation, word\_choice, missing\_word, extra\_word, spelling, punctuation, other. Коды стабильны; добавление через миграцию.

### 4.9. Голос (этап 2)

**FR-VOI-1. Диалог в режиме push-to-talk.**

1. Ученик зажимает кнопку (или нажимает и отпускает), модуль voice.js записывает звук через AudioWorklet в PCM 16-бит, моно, 16 кГц (без ffmpeg и без зависимости от формата, который выбирает браузер).
2. Запись до 30 секунд (проверить лимит выбранного режима SpeechKit) отправляется POST-запросом (application/octet-stream) на сервер.
3. Сервер валидирует размер и длительность, вызывает Transcriber, возвращает ученику распознанный текст (он видит, как его поняли).
4. Распознанный текст идёт в тьютор (4.7); ответ модели синтезируется Synthesizer.
5. Аудио ответа сохраняется во временное хранилище с TTL 24 часа и отдаётся по подписанной ссылке; воспроизведение запускается после жеста пользователя.

**FR-VOI-2. Целевая задержка** от конца записи до начала воспроизведения: p50 не более 4 с, p95 не более 8 с; в интерфейсе индикатор этапов («слушаю», «думаю», «говорю»). Потоковый вариант (streaming ASR и TTS) вне MVP, интерфейсы его допускают.

**FR-VOI-3. Квоты:** учитывается длительность аудио, отправленного в ASR, и число символов, отправленных в TTS. Лимит минут в месяц по тарифу.

**FR-VOI-4. Упражнение read\_aloud.** Эталонная фраза показывается ученику, запись распознаётся, затем токены сравниваются с эталоном выравниванием (наибольшая общая подпоследовательность на нормализованных словах). Для каждого слова статус: совпало, пропущено, заменено. Если ASR отдаёт уверенность по словам, она учитывается как вспомогательный сигнал. Ученику показывается «разборчивость» (доля совпавших слов) и слова, которые распознаны иначе, плюс эталонное аудио для сравнения.

**Ограничение, которое нужно отразить в интерфейсе и рекламе:** это оценка разборчивости, а не фонемный разбор произношения. ASR склонен восстанавливать слово по контексту и может «простить» ошибку. Формулировки в UI: «разборчивость», а не «правильность произношения».

**FR-VOI-5. Приватность.** Записи ученика не сохраняются (обрабатываются в памяти). Логируются только длительность, провайдер, задержка и стоимость.

**FR-VOI-6. Деградация.** Нет микрофона, отказ в доступе, ошибка ASR — упражнение можно пропустить без штрафа, диалог переключается в текстовый режим.

### 4.10. Коучинг, статистика и напоминания

- **FR-COA-1. Дашборд ученика:** серия дней (день засчитывается при хотя бы одном завершённом занятии; одна «заморозка» в неделю), минуты за неделю против цели, число выученных слов, освоение навыков по уровням, ближайшие повторы.
- **FR-COA-2. Недельный отчёт** (воскресенье 18:00 по часовому поясу ученика): сводка цифр, 3 слабых места, рекомендация. Текст рекомендации генерируется моделью коротко (до 120 слов) на основе структурированной сводки; при ошибке модели используется статический шаблон.
- **FR-COA-3. Напоминания по email** (отправка из worker): ежедневное (в выбранное время, только если сегодня не было занятия; не чаще 1 в день); возврат после пропуска 3 и 7 дней со ссылкой на пятиминутное занятие; об окончании доступа за 7 дней, за 1 день и после окончания. В каждом письме ссылка отписки (подписанная), настройки в профиле. Web Push и Telegram вне MVP.
- **FR-COA-4. Возвращение после паузы:** первое занятие после перерыва от 3 дней короткое (5 минут), с упором на повторение и дружелюбным текстом.

### 4.11. Биллинг и доступ

**FR-BIL-1. Тарифы** (таблица plans, правятся в админке): код, название, длительность в месяцах (1, 3, 12), цена в копейках (только RUB), активность, квоты. Автопродления нет.

**FR-BIL-2. Trial.** Выдаётся один раз на аккаунт при подтверждении email, длительность в конфиге (TRIAL\_DAYS, по умолчанию 3). Квоты trial отдельные и меньше платных. Защита от злоупотребления: нормализованный email (нижний регистр, без plus-адресации), подтверждение обязательно, лимит регистраций с одного IP, детектор одноразовых почтовых доменов (список в конфиге).

**FR-BIL-3. Правило доступа:** доступ есть, пока текущее время меньше максимума из ends\_at всех entitlements пользователя. Без доступа вход и кабинет работают, платёжный экран открыт, занятия закрыты. Новая оплата продлевает от максимума из «сейчас» и текущего конца доступа.

**FR-BIL-4. Сценарий оплаты:**

1. Пользователь выбирает тариф, POST /billing/checkout создаёт заказ orders (статус pending) с ключом идемпотентности.
2. Сервер создаёт платёж в ЮKassa (redirect-подтверждение, return\_url, order\_id в метаданных, данные для чека по требованиям провайдера) и перенаправляет пользователя.
3. На return\_url страница «проверяем оплату» опрашивает статус заказа через HTMX (каждые 2 секунды, до 60 секунд).
4. Вебхук payment.succeeded: сервер не доверяет телу, а запрашивает платёж у API ЮKassa по идентификатору и сверяет сумму, статус и order\_id. В одной транзакции: заказ → paid, запись в payments (уникальный provider\_payment\_id), создание entitlement. Повторные вебхуки безопасны.
5. Задача reconcile\_orders каждые 10 минут проверяет у провайдера pending-заказы старше 5 минут (страховка от потерянных вебхуков).
6. Событие payment.canceled переводит заказ в canceled. Письмо о продлении доступа отправляется после paid.

**FR-BIL-5. Возвраты и ручные действия:** в админке; возврат вызывает API провайдера, администратор выбирает, сокращать ли доступ. Ручная выдача или продление доступа пишутся в audit\_log с причиной.

**FR-BIL-6. Квоты** (значения по умолчанию, меняются в админке и конфиге): сообщений тьютору в день — trial 30 / платный 200; минут голоса в месяц — trial 10 / платный 300; проверок письма в день — trial 3 / платный 10. Счётчики в usage\_counters, атомарное увеличение через UPSERT. Мягкое предупреждение при 80%.

## 5. Интеграции: интерфейсы внешних сервисов

Ключевое требование заказчика: любой внешний сервис (LLM, распознавание речи, синтез, оценка произношения, платежи, почта, хранилище) подключается через интерфейс и заменяется конфигурацией без изменения бизнес-логики.

### 5.1. Общие требования к адаптерам

1. Каждый вызов принимает context с таймаутом; значения таймаутов в конфиге.
2. Повторы: до 2 раз с экспоненциальной паузой и джиттером, только для сетевых ошибок, 5xx и 429; не повторять неидемпотентные операции без ключа идемпотентности.
3. Circuit breaker на каждого провайдера: после серии ошибок провайдер временно исключается из цепочки.
4. Цепочка провайдеров (fallback chain) задаётся по назначению (purpose) в конфиге.
5. Каждый вызов пишет строку в llm\_calls или speech\_calls: провайдер, модель, назначение, объём (токены, секунды, символы), стоимость по прайсу из конфига, задержка, статус, trace\_id.
6. Адаптеры не логируют содержимое запросов и ответов за пределами отладочного режима (в логах нет текстов учеников и голоса).
7. Для каждого интерфейса есть заглушка (mock) для тестов и локальной разработки.
8. Секреты только из переменных окружения.

### 5.4. Yandex SpeechKit: особенности (проверить по документации при реализации)

- **Распознавание.** Английский поддерживается (en-US). Для коротких записей использовать синхронный режим; формат на входе LPCM 16 кГц, 16 бит, моно — это совпадает с тем, что собирает браузерный модуль, и не требует перекодирования. Уточнить в квотах SpeechKit: максимальную длительность и размер синхронного запроса (по умолчанию закладываем 30 секунд и 1 МБ).
- **Синтез.** Английский голос в списке голосов на момент составления ТЗ один (john, мужской); актуальный список проверить. Разметка управления произношением полностью поддерживается только для русского текста, поэтому на английском тексте управление произношением через разметку не планируем. Скорость речи регулируется параметром.
- **Последствия для продукта:** для аудирования доступен один голос и один акцент. Это известное ограничение MVP; компенсируется регулируемой скоростью и возможностью подключить второй провайдер TTS через тот же интерфейс.
- **Кэш TTS:** ключ — SHA-256 от (провайдер, голос, скорость, формат, текст). Фиксированный контент (упражнения, слова, примеры) озвучивается заранее задачей prewarm\_tts при публикации и хранится бессрочно; реплики тьютора хранятся 24 часа. Это основной способ экономии на синтезе.
- **Длинный текст** разбивается по предложениям, не дольше лимита одного запроса (уточнить).

### 5.6. Контроль стоимости

- Таблицы llm\_calls и speech\_calls, дашборд в админке: стоимость по дням, по назначению, на пользователя; топ-20 самых затратных пользователей.

## 7. HTTP-интерфейс

### 7.1. Соглашения для HTMX и Templ

1. Если запрос содержит заголовок HX-Request, сервер возвращает HTML-фрагмент, иначе полную страницу (все страницы должны открываться по прямой ссылке и обновлением).
2. После успешного POST навигация выполняется заголовком HX-Redirect, частичное обновление — возвратом фрагмента.
3. Ответы 4xx, содержащие фрагмент с ошибкой формы, должны подменяться в DOM (настройка responseHandling в HTMX 2); для 5xx показывается общий фрагмент «что-то пошло не так, повторите».
4. Стриминг тьютора — расширение SSE для HTMX; события token, done, error.
5. HTMX, SSE-расширение и Pico.css кладутся в /web/static с версией в имени файла, без загрузки с CDN. Сторонние скрипты не подключаются, кроме виджета Yandex SmartCaptcha на страницах входа, регистрации и сброса пароля.
6. Заголовки безопасности на всех ответах: Content-Security-Policy (script-src 'self' плюс источник SmartCaptcha, без inline-скриптов; стили только 'self'), Strict-Transport-Security, X-Content-Type-Options: nosniff, Referrer-Policy: same-origin, Permissions-Policy (микрофон разрешён только для себя).

## 8. Контент-пайплайн

Принцип: ученику показывается только проверенный контент. Генерация идёт заранее, пакетами, и проходит автоматические проверки и ревью человеком.

### 8.1. Этапы

1. **Скелет программы.** Список навыков, зависимостей и формулировок «умею» составляется вручную с помощью LLM, утверждается человеком и импортируется в админку из YAML или CSV. Это самый важный шаг: ошибка в порядке навыков ломает всё обучение.
2. **Генерация.** Задача generate\_exercises(skill, type, count, prompt\_version, model). Промпт содержит описание навыка и уровень, ограничение лексики (слова не выше уровня), JSON-схему типа упражнения, 2–3 образца и требования к объяснению на русском. Ответ валидируется по JSON-схеме (5.2, Structured).
3. **Автоматическая проверка** (каждая должна пройти):
   - **Решение второй моделью.** Упражнение (без ключа) решает модель из другой цепочки; расхождение с ключом означает отправку на ручное ревью с пометкой или отклонение.
   - **Один правильный ответ** для заданий с выбором (проверка тем же способом с перебором вариантов).
   - **Уровень текста:** доля слов выше заявленного уровня по частотному списку не более 5%, длина предложения в допустимых пределах для уровня.
   - **Дубли:** content\_hash и похожесть по триграммам (pg\_trgm) выше 0,8.
   - **Тематический фильтр:** стоп-лист чувствительных тем (политика, насилие, взрослый контент, реклама).
   - **Допустимые ответы** у translate\_to\_en: не менее двух вариантов формулировки.
4. **Ревью человеком** в админке: approve, reject, edit. Целевая скорость не ниже 60 упражнений в час при горячих клавишах и массовых действиях. Для первых 100 упражнений каждого типа проверяется всё; затем выборочный контроль плюс обязательная проверка всего, что автоматика пометила.
5. **Публикация:** статус published, задача prewarm\_tts озвучивает аудио (этап 2).
6. **Мониторинг после публикации:** если после 50 попыток доля верных ответов ниже 15% или выше 98%, упражнение получает пометку на пересмотр; три жалобы за неделю дают статус flagged (4.13).

### 8.2. Объёмы для MVP и трудозатраты

- A1–A2: около 65 навыков × 12 упражнений ≈ 780 упражнений, 800–1000 слов с примерами, 120 вопросов теста уровня.
- Ревью: около 1 минуты на упражнение, то есть 13–15 часов на весь объём MVP. Закладывается в план работ.

### 8.3. Промпты и их качество

- Промпты хранятся в prompt\_versions, активная версия одна на имя; правки только новой версией, откат — переключением флага.
- Для каждого критичного промпта (тьютор, анализ ошибок, проверка письма, генерация) есть эталонный набор примеров в /docs/evals и автоматический прогон при смене версии или модели; результат сравнивается с предыдущей версией, регресс блокирует активацию (подтверждение вручную).
- Любой вызов LLM пишет prompt\_version\_id в llm\_calls, чтобы связывать качество с версией.

## 9. Нефункциональные требования и эксплуатация

### 9.1. Безопасность

1. Базовый уровень: чек-лист OWASP ASVS уровня 1 для веб-приложений, проверяется перед запуском.
2. TLS 1.2+ (Caddy), HSTS, cookies Secure + HttpOnly + SameSite=Lax, CSRF на всех изменяющих запросах (4.1).
3. XSS: автоэкранирование Templ; запрещено использовать templ.Raw и небезопасный вывод для пользовательского текста и ответов модели; ответы тьютора выводятся как текст.
4. SQL только через sqlc и параметризованные запросы; динамические фрагменты запрещены.
5. Секреты только в переменных окружения, файл .env не в репозитории; ротация ключей провайдеров возможна без пересборки.
6. Лимиты запросов (на пользователя или IP):

| Маршрут | Лимит |
| --- | --- |
| вход | 5 неудач / 15 минут на (IP, email), затем капча |
| регистрация | 3 в час на IP |
| сброс пароля | 3 в час на email |
| сообщения тьютору | 20 в минуту |
| ответы на упражнения | 120 в минуту |
| запись голоса | 10 в минуту |
| создание платежа | 10 в час |
| API админки | 600 в минуту |

7. Админка: проверка роли на сервере, журнал аудита, двухфакторная защита TOTP для роли admin (этап 3, до этого сильный пароль и ограничение по IP на уровне Caddy по желанию).
8. Зависимости: govulncheck и npm audit в CI, обновление зависимостей раз в месяц.
9. Сервер: вход по SSH только по ключам, ufw с открытыми 22, 80, 443; PostgreSQL слушает только внутреннюю сеть Docker; контейнеры без root; автоматические обновления безопасности ОС.
10. Логи не содержат паролей, токенов, текстов диалогов и персональных данных (только числовой user\_id и request\_id).

### 9.2. Производительность

- Время ответа страниц (без вызовов LLM) p95 не более 300 мс; проверка ответа на упражнение p95 не более 150 мс.
- Начало потока ответа тьютора (первый токен) p50 не более 2 с.
- Пул соединений pgxpool: до 20 для web, до 10 для worker; параметры Postgres подбираются под ОЗУ (shared\_buffers около 25%).
- Нагрузочный тест (k6): 150 одновременных сессий в течение 10 минут без деградации выше указанных порогов и без ошибок более 1%.

### 9.3. Надёжность

- Целевая доступность 99,5% в месяц (без учёта сбоев внешних провайдеров, для которых есть деградация, 4.7 и 4.9).
- Корректная остановка (graceful shutdown) web и worker; health-проверки; политика restart в Docker.
- Деплой допускает паузу до 10 секунд; миграции обратно совместимы (сначала расширение схемы, затем смена кода, затем очистка), чтобы откат образа не требовал отката БД.

### 9.4. Наблюдаемость и алерты

- Логи slog в формате JSON с request\_id; метрики Prometheus на отдельном внутреннем порту (задержки HTTP, ошибки, задачи очереди, задержки и ошибки провайдеров, стоимость).
- Внешняя проверка доступности (любой сервис мониторинга) для главной страницы и /healthz.
- Алерты в Telegram-бота разработчика: 5xx выше порога, упавшие задачи очереди, ошибки вебхука платежей, превышение бюджетных порогов, заканчивающееся место на диске, неуспешный бэкап.

### 9.5. Резервное копирование и восстановление

- Ежедневный pg\_dump (custom-формат), шифрование (age или gpg), загрузка в S3-совместимое хранилище **другого** российского провайдера; хранение 14 ежедневных и 8 еженедельных копий.
- Каталог медиа (кэш TTS) восстанавливается заново из текстов, поэтому в критичный бэкап не входит, но синхронизируется, чтобы не платить за повторный синтез.
- Если потеря до 24 часов станет неприемлемой (после появления значительного числа платящих), включается архивирование WAL (WAL-G) для восстановления на момент времени.
- Ежемесячный тест восстановления на чистой машине; целевое время восстановления (RTO) 4 часа, допустимая потеря данных (RPO) 24 часа на MVP.

### 9.6. Тестирование и качество кода

- **Юнит-тесты:** проверка ответов и нормализация, алгоритм теста уровня (симуляция), планировщик, обёртка FSRS, квоты, конечный автомат заказов.
- **Интеграционные** (testcontainers-go, настоящий Postgres): сценарии аутентификации, идемпотентность вебхука оплаты, прохождение занятия, права доступа.
- **Контрактные тесты адаптеров** на записанных ответах провайдеров (httptest).
- **Оценки промптов (evals)** по эталонным наборам (8.3).
- **E2E (Playwright):** регистрация, подтверждение, тест уровня, занятие, оплата на заглушке платёжного провайдера.
- **CI блокирует слияние**, если не проходят тесты, go vet, golangci-lint, govulncheck, проверка актуальности сгенерированного кода (templ, sqlc, OpenAPI-типы). Покрытие ключевых пакетов (auth, billing, planner, exercises, placement) не ниже 70%.

### 9.7. Среды, сервер и деплой

- **Среды:** локальная (docker compose, провайдеры-заглушки), прод. Staging по желанию: второй compose-проект на том же VPS с другим доменом.
- **Стартовый размер VPS (предположение, подтвердить нагрузочным тестом):** 4 vCPU, 8 ГБ ОЗУ, NVMe от 80 ГБ; на одной машине web, worker, PostgreSQL и Caddy. Тяжёлых вычислений нет (все модели внешние), узкое место — соединения SSE и база.
- **CI/CD:** сборка и тесты в CI, образы в реестр, деплой по SSH: docker compose pull, миграции одноразовым контейнером, затем up -d; откат — предыдущим тегом образа.
- **Домен и почта:** SPF, DKIM, DMARC для отправляющего домена до первого письма.
- Примеры конфигураций — в приложениях A–C.

### 9.8. Работа в формате «один разработчик + AI-ассистент»

1. В корне репозитория файл AGENTS.md (или аналог) с соглашениями: структура, стиль, запрет на ORM, правила для Templ/HTMX, команды сборки и тестов.
2. Задачи ставятся вертикальными срезами по разделам ТЗ (например, «FR-AUTH-1…3 с тестами»), не «весь модуль».
3. Для критичной логики (аутентификация, платежи, CSRF, квоты) тесты пишутся первыми, код ассистента проходит отдельный ручной ревью.
4. Параметры внешних API (SpeechKit, ЮKassa, OAuth Яндекса и VK, LLM-провайдер) берутся из официальной документации и вставляются в контекст ассистента; параметры по памяти модели не используются.
5. SQL, сгенерированный ассистентом, проверяется глазами и EXPLAIN на больших таблицах; все изменения схемы только через миграции.
6. Решения, которые нельзя восстановить из кода (почему выбрано то или иное), записываются коротко в /docs/adr.
7. Версии зависимостей фиксируются; обновление — отдельной задачей с прогоном всех тестов.

## 10. Метрики успеха и юнит-экономика

### 10.1. Продуктовые метрики (стартовые ориентиры, уточняются по пилоту)

| Метрика | Определение | Ориентир |
| --- | --- | --- |
| Активация | дошёл до первого завершённого занятия в течение 24 часов после подтверждения email | не ниже 60% |
| Завершение занятий | доля начатых занятий, доведённых до итогового экрана | не ниже 70% |
| Регулярность | доля активных платящих, занимающихся 3 и более дней в неделю | не ниже 40% |
| Удержание D7 / D30 | возврат на 7-й и 30-й день | замеряем в пилоте, цель задаётся после первых данных |
| Конверсия trial → оплата | доля оплативших среди завершивших trial | замеряем в пилоте |
| Прогресс | доля регулярно занимающихся, повысивших уровень на подуровень по независимому повторному тесту за 3 месяца | не ниже 40% |

События аналитики пишутся в таблицу events (user\_id, name, props jsonb, created\_at; добавляется миграцией этапа 1): registered, email\_verified, onboarding\_done, placement\_done, lesson\_started, lesson\_finished, paywall\_shown, checkout\_started, paid, chat\_started, voice\_used, report\_sent, reminder\_sent, reminder\_clicked. Внешние трекеры не подключаются.

### 10.2. Технические метрики

p95 из раздела 9.2; доля 5xx ниже 1%; доля ошибок провайдеров ниже 2% при работающем fallback; доля заданий, помеченных жалобами, ниже 3% от показов.

### 10.3. Юнит-экономика

Себестоимость активного пользователя за месяц считается автоматически из llm\_calls, speech\_calls и тарифа инфраструктуры:

`cost = сообщения × (токены_вход × цена_вход + токены_выход × цена_выход) + минуты_голоса × (цена_ASR + цена_TTS) + доля_инфраструктуры + комиссия_платёжки`

| Параметр | Откуда берётся |
| --- | --- |
| цены токенов LLM, цена ASR и TTS | прайсы выбранных провайдеров, заносятся в конфиг (цены в ТЗ намеренно не фиксируются) |
| объём использования | usage\_counters и логи вызовов |
| инфраструктура | счёт хостинга, делённый на число активных пользователей |
| комиссия платёжки и налог | по условиям ЮKassa и режиму налогообложения (уточнить) |

**Правило тарифа:** себестоимость переменных затрат активного платящего пользователя не выше 25% от выручки с него в месяц; квоты (4.11) подбираются так, чтобы худший случай (пользователь выбрал все лимиты) не уходил в минус.

## 11. План работ и этапы

Оценки для одного разработчика с AI-ассистентом при полной занятости. Сроки ориентировочные.

Репозиторий, CI, docker compose, конфиг, логи, миграции, каркас Templ и Pico, каркас Vue-админки со входом, деплой на VPS с Caddy, ежедневный бэкап и проверка восстановления. **Приёмка:** деплой по тегу одной командой; вход в админку; /healthz; бэкап восстанавливается на чистой машине.

### Этап 2. Голос (3–4 недели)

voice.js (AudioWorklet), адаптеры Transcriber и Synthesizer для Yandex SpeechKit, голосовой диалог, read\_aloud, listening и dictation, предварительная озвучка, квоты голоса. **Приёмка:** p50 задержки не более 4 с; работает в Chrome и Safari на десктопе, в Chrome на Android и Safari на iOS; при отказе в микрофоне сервис деградирует в текстовый режим.

### Этап 3. Удержание и контент (4–6 недель)

Проверка письма, недельные отчёты, сценарии возвращения, контент B1 и B2, TOTP для админов, правки по результатам пилота, нагрузочные тесты на реальных данных.

## 12. Риски

| Риск | Меры |
| --- | --- |
| ЮKassa ограничит возможности для самозанятого или откажет в подключении | запасной провайдер за интерфейсом (CloudPayments, Т-Банк, Prodamus); при необходимости переход на ИП |
| Доход приблизится к лимиту самозанятого | мониторинг выручки в админке, заранее решить вопрос перехода на ИП |
| Open-weight модели ошибаются в грамматике и ключах | решение второй моделью, ревью, более сильная модель для генерации, evals, жалобы |
| Один английский голос TTS ограничивает аудирование | регулируемая скорость, второй провайдер за интерфейсом, браузерный TTS для слов |
| ASR «прощает» ошибки, оценка произношения грубая | честные формулировки «разборчивость», этап 4 |
| Стоимость LLM и голоса съедает маржу | квоты, кэш, бюджетные пороги, дешёвые цепочки для фоновых задач, ежедневный отчёт по затратам |
| Недоступность провайдера (LLM, SpeechKit) | цепочки fallback, circuit breaker, деградация без списания квоты |
| Утечка данных, захват аккаунта | раздел 9.1, минимизация данных, подтверждение email, лимиты |
| Нарушение 152-ФЗ | консультация юриста, хранение в РФ, уведомление РКН, политика, согласие |
| Лицензии словарей и списков | использование открытых источников или проверка условий до импорта |
| Злоупотребление trial | нормализация email, подтверждение, лимиты по IP, список одноразовых доменов |
| SSE ломается из-за буферизации прокси | flush\_interval -1 в Caddy, тест на боевом окружении |
| Prompt injection, токсичный ввод | изоляция пользовательского текста, ограничения вывода, лимиты |
| Проблемы микрофона и автовоспроизведения на iOS/Safari | запуск аудио по жесту, проверка на реальных устройствах, текстовый режим |
| Выгорание единственного разработчика, потеря знаний | простой стек, ADR, документация, автоматизация деплоя и бэкапов |
| Низкое удержание | коучинг, напоминания, короткие занятия, пилот и итерации по данным |

Caddy сам получает и продлевает TLS-сертификаты для домена. Порт метрик в проксирование не включается. flush\_interval -1 отключает буферизацию, без чего SSE-стрим не работает.

## Приложение C. Переменные окружения (только имена)

Процесс: APP\_ENV, APP\_BASE\_URL, APP\_CONFIG\_FILE, HTTP\_ADDR, METRICS\_ADDR, LOG\_LEVEL, SHUTDOWN\_TIMEOUT.

Данные и продукты: DATABASE\_URL, POSTGRES\_USER, POSTGRES\_PASSWORD, POSTGRES\_DB, MEDIA\_SIGN\_KEY, TRIAL\_DAYS.

Почта: SMTP\_HOST, SMTP\_PORT, SMTP\_USER, SMTP\_PASSWORD, MAIL\_FROM.

Провайдеры: LLM\_PRIMARY\_KEY, LLM\_FALLBACK\_KEY, LLM\_STRONG\_KEY, YC\_SPEECH\_KEY, YC\_FOLDER\_ID, YK\_SHOP\_ID, YK\_SECRET, YANDEX\_OAUTH\_CLIENT\_ID, YANDEX\_OAUTH\_CLIENT\_SECRET, VK\_OAUTH\_CLIENT\_ID, VK\_OAUTH\_CLIENT\_SECRET, SMARTCAPTCHA\_CLIENT\_KEY, SMARTCAPTCHA\_SERVER\_KEY, TELEGRAM\_BOT\_TOKEN, TELEGRAM\_CHAT\_ID.

- Локальный шаблон значений: `.env.example`; рабочий файл `.env` в репозиторий не попадает.

## Приложение D. Чек-лист запуска
